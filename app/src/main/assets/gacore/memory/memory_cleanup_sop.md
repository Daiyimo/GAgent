# 记忆整理 SOP

## 核心原则: 存在性编码
LLM 自身是压缩器+解码器。L1 只需让它**意识到某类知识存在**, 它就能 tool call 自行取用深层内容。
**L1 本质 = 用最短词数表达: 什么场景下有什么记忆可用。** 两类内容统一 ROI 评估:
- **存在性指针**: 指向 L2/L3 知识的最短触发词。
- **行为规则**: 不提醒就会犯的错(致命/高频均可, ROI 过门槛即留)。
- ROI = (不放这几个词的犯错概率 × 代价) / 每轮词数成本。

## 快速判断
- **该留**: 反直觉触发词——没提示就想不到去查 SOP 的场景词。如 `tmwebdriver_sop(httponly cookie)`: 没这个词就不会想到取 cookie 要查它。
- **该删**: 名字翻译(`proxy-pool/(代理池)`→直接 `proxy-pool`) | 内容描述(实现细节属 SOP 内部, 非触发场景) | 直觉能力(不提醒也想得到=0收益白交成本) | 冗余(L3 已覆盖/L1 他行已含)。

## 压缩四原则
1. 命名自解释 > 加描述: SOP 名能说清的不加注释; 改名 ROI 常高于改 L1。
2. 存在性集合最小描述: 相近条目可被同一上位场景覆盖→用集合名(如 `qq/飞书/企微操作`→`im操作:*_im_sop`); 子项自解释则只列名。
3. 条目 = 场景↔方案存在性(如 `视频理解:yt-dlp取字幕`); 括号内**只放反直觉触发词**, 翻译/内容描述/实现细节全是浪费。
4. 分层归位: 带行为规则或高频高 ROI 的进上方场景行, 纯存在性指针归 L2/L3 平铺列表。

## 整理流程
1. 逐行读 L1, 按 `|` 拆片段分类: 存在性指针/RULES/翻译/内容描述/实现细节/冗余。
2. 先清 RULES: 全局高 ROI→留; 特定场景/低危险→降级 L3 或删。
3. 再清指针: 是否表达场景↔方案存在性; 触发词只在反直觉时加, 其余删。
4. 查 L3 文件名是否自解释(能改名解决就不加 L1 描述); 验证总行数 ≤30。

**红线**: 记忆修改是持久性伤害, 错误每轮复利。L1 只能词级 patch, 禁 overwrite; 产生误导应及时修正 L1 或记忆更名。
