# 记忆管理 SOP

## 0. 核心公理(最高优先级)
1. **行动验证原则**: 写入 L1/L2/L3 的信息必须源自成功的工具调用结果(shell 成功/file_read 确认/代码跑通)。严禁把模型固有知识、推理猜测、未执行计划、未验证假设当事实写入。口号: **No Execution, No Memory**。
2. **神圣不可删改性**: 经行动验证的有效配置/避坑指南/关键路径, 重构(GC)时严禁丢弃——可压缩文字、可迁层级(L2→L3), 不可丢准确性与可追溯性。修改记忆极度小心: 尽量不 overwrite/不 code_run, 只少量 patch, 改不动宁愿不改。
3. **禁止存储易变状态**: 时间戳/临时 Session ID/运行中 PID/具体绝对路径/连接的设备信息等高频变化数据一律不存。
4. **最小充分指针**: 上层只留能定位下层的最短标识, 多一词即冗余。

## 层级架构
```
L1: global_mem_insight.txt (极简索引, ≤30行) → 导航指向
L2: global_mem.txt (事实库, 现短会膨胀) → 详细引用
L3: ../memory/ (记录库, .md/.py)
L4: ../memory/L4_raw_sessions/ (历史会话, scheduler 自动收集, 可定位过往上下文)
```

## 各层职责
### L1 (global_mem_insight.txt)
- 职责: 为 L2/L3 提供极简导航, 确保关键能力可被发现。≤30 行(硬约束), <1k tokens; 严禁细节(除极高频任务)。
- 内容 = 两层「场景关键词→记忆定位」+ RULES:
  - 第一层: 高频场景 key→value(直接给 sop/py/L2 section 名), 自包含名称只写一词不重复翻译。
  - 第二层: 低频场景仅列关键词, 用时 read L2 / ls L3 自行定位。
  - 场景触发词极重要(不索引=不知有此能力), 但严禁写 How-to 细节。
  - RULES = 压缩版避坑准则: 红线-致命型(违反即进程终止/崩溃, 如`禁无条件杀python(会杀自己)`) + 红线-隐蔽型(不报错但结果错) + 高频犯错点。
- **禁止**: 密码/API Key(允许内联非敏感触发参数如代理端口); How-to/详细解释; 特定任务技术细节(归 L3); 更严禁写日志记录。修改只允许少量 patch, 禁 overwrite/code_run。

### L2 (global_mem.txt)
- 全局环境性事实(路径/凭证/配置/常量), 按 `## [SECTION]` 组织; 膨胀可接受; 变化时同步 L1 对应导航行(只导航)。
- **禁止**: 易变状态、猜测、大模型可推理的通用常识。

### L3 (../memory/)
- 只记: 跨会话仍重要、且难以通过少量 file_read/web_scan/简单脚本快速重建的要点; 优先写任务特有隐藏前置条件与易踩坑点(遗忘=高成本重试)。满足复用前提下尽可能短。
- 不记: 普通操作步骤、几步探测可重建的路径/状态。
- 形式: `*_sop.md`=极简「关键前置+典型坑」清单(禁长篇教程); `*.py`=仅封装高复用、逻辑复杂、不想每次重新推理的流程。

## L1 ↔ L2/L3 同步规则
| 操作 | L1 同步 |
|---|---|
| 新增场景 | 默认低频→L3列表加文件名(自解释不加描述; 反直觉场景才加括号触发词) |
| 删除场景 | 删对应关键词/映射行 |
| 修改值 | 不影响场景定位则不动 L1 |
| 发现通用避坑规律 | 压缩为一句进 RULES |

> **同步红线**: L1 只写关键词/名称, 禁搬细节; 括号内只写反直觉触发词(2-4字), 禁写机制/方法/步骤; 评估 token 数与索引效用。
> 反例: ❌ sop_name(场景A:方法1+方法2) → ✅ sop_name(场景A); 名字自解释时 ❌ discord_slate_sop(Slate输入框) → ✅ discord_slate_sop。

## 分层决策("这条信息放哪层?")
1. 环境特异性事实(IP/非标路径/凭证/ID/密钥, Zero-shot 无法生成)→ L2, 再按频率进 L1 第一层或第二层。
2. 通用操作规律(全局避坑/排查方法)→ L1 RULES(仅限1句压缩)。
3. 特定任务技术(艰难尝试才成功且未来复用, 如微信解析参数/特定坐标/工具配置)→ L3。
4. 都不是 = 通用常识/冗余: 严禁存储, 直接丢弃。
